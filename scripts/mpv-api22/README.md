# API 22 mpv candidate PoC

The standalone workflow `.github/workflows/mpv-api22-candidate.yml` downloads the official mpv-android 2024-11-16 x86 release and verifies its SHA-256 and declared minSdk21. It runs only on the isolated `poc/mpv-api22-validation` branch or manual dispatch. The workflow does not replace My Cinema's player or use Quark credentials. Its synthetic sample has 1080p15 H.264/AAC, two SRT streams, and an attached DejaVu font.

The original `scripts/libmpv-runtime-api22.sh` gate was tightened: it requires one default-flavor APK, an API22-compatible manifest, an explicit successful install, an activity start, and libmpv mapped in the actual process. A successful build or adb exit status alone is not enough.

## Recorded results

- [Run 42572987605](https://github.com/StQuasimodo/Media-Library/actions/runs/42572987605), source `e2c8cc471d0404a860fabda8234714a07eb0ddfa`: API22 x86 installation, activity launch and libmpv mapping succeeded. Script observed two subtitle tracks, independent selection and position values; pause, seek to 25 seconds and resume clock progression passed. `secondary-sub-scale` returned unavailable and independent subtitle scaling failed. Screenshot was blocked by the Android immersive-mode prompt.
- [Run 42573728614](https://github.com/StQuasimodo/Media-Library/actions/runs/42573728614), source `b80e8aa`: same core assertions, with a font attached to the Matroska file and mpv-rendered frame capture. Secondary scale still returned nil. Both the display screenshot and composed frame were black with no visible subtitles, so simultaneous visual display is **not verified**. Logs report that libass could not find its chosen font provider. The run correctly fails the independent scaling gate.

Actions artifacts `mpv-api22-candidate-evidence` contain checksums, sample, `probe.txt`, process maps, memory snapshot, logcat, `screen.png`, and (where available) `frame.png`. The isolated third-party release demonstrates neither My Cinema integration nor ARMv7 runtime compatibility; no physical television or real Quark streaming was tested. The original current-master native build uses moving inputs and has not become a reproducible API21 source build. Further work must resolve subtitle rendering/font setup, test independently enabling/disabling each track and other style attributes, and evaluate an API21-compatible newer mpv before selecting a production engine.

## 2026-04-25 candidate retest

[Run 42575118678](https://github.com/StQuasimodo/Media-Library/actions/runs/42575118678), source `9cff4d3f9bd921904a78932f1d2d05671dffdcf6`, used the official 2026-04-25 x86 APK, SHA-256 `2cf77b8cc654b9a257602aff0ad7f8c7e933dd91b99a29f9ca02f3c397e6b1dc`, manifest minSdk21. A configured DejaVu font directory was loaded by libass. Replacing the single long cue with repeated one-second cues caused both subtitle text properties to become populated. The captured [composed frame](../../artifacts/mpv-api22-poc/dual-subtitles-api22.png) visibly contains both streams at different positions. This supports simultaneous SRT rendering for this synthetic sample in the API22 x86 emulator, not arbitrary subtitles or device performance.

Track selection, position settings, both subtitle text assertions, pause, 25-second seek and resume passed. Independent secondary scale remained unavailable (`secondary-sub-scale` returned nil), so the workflow failed as designed. This test does not establish independent font/color settings, external subtitles, ARMv7 loading, real Quark streaming, or real-TV rendering. The black background is intentional in the generated sample; the capture is the player's composed frame, not proof of a physical display.

## Independent visibility, delay and candidate backport

[Run 42576183725](https://github.com/StQuasimodo/Media-Library/actions/runs/42576183725), source `81b5ddd`, tested the same official API21-compatible 2026-04-25 x86 APK on API22. The two `sub-visibility` properties could be independently toggled and queried, and independent +0.4/-0.4 second delay properties could be set and read back. This is property-level evidence; separate screenshot/time-based proof that disabling or offsetting each cue affects the rendered image is still required. The prior dual-subtitle frame, playback, seek and pause checks remained passing. The workflow remained failed because `secondary-sub-scale` was unavailable.

Upstream mpv added `secondary-sub-scale` in [commit 8ab3f8b66dcf2c2471f4dbba5cee21cda06843b7](https://github.com/mpv-player/mpv/commit/8ab3f8b66dcf2c2471f4dbba5cee21cda06843b7), 2026-07-04 UTC. The tested 2026-04-25 APK identifies its mpv source as `9ce79bcaa0132660a2e45b6bfc1fb0c199665277`; later mpv-android 2026-08-11 and 2026-09-17 source configurations declare minSdk23. A local `patch --dry-run -p1` of the upstream change against the 9ce79bc source reported all files applicable, but two hunks needed fuzz (1 and 2), so this is only a feasibility probe. It has not been reviewed, built, linked into an APK, or tested on either ABI. An actual backport requires exact source/dependency/toolchain pinning, manual review of fuzzy hunks, rebuild of ARMv7 and x86, and runtime checks of subtitle rendering and independent styling before any engine decision.
