# TV 播放质量验证

播放器验收分为传输正确、可连续播放、目标设备可用三个范围。合成片在 API22 模拟器通过，只记录该样片和网络条件的结果。

| 验证层次 | 测试条件和通过标准 |
| --- | --- |
| 本地传输测试 | 使用生产 `MediaTransfer` 和本机 HTTP 服务，验证多个 4 MiB 区间逐字节一致。分别阻塞地址获取、HTTP 响应头、响应体和下游写入，确认只有被阻塞的阶段显示当前等待。模拟断流后从确切字节续接。 |
| Android 基础回归 | API22 在受控夸克协议和外部 WebDAV 上真正解码 1080p H.264/AAC；覆盖断流、地址续期、拖动、暂停、重连、续播、外挂字幕及同签名升级。原有低码率长播继续运行。 |
| 高码率 1080p | 28 秒运动样片，H.264/AAC，1920×1080、30 fps，文件实测至少 20 Mb/s。通过标准为 12 秒内首帧，在随后 12 秒窗口中播放时钟推进至少 85%、显示至少理论帧数的 65%，最长出帧间隔小于 1.8 秒，且没有播放错误。记录实际掉帧，不能从单次通过外推到整片。 |
| 1080p 卡顿复现 | 使用同一文件和同一播放器，在第二个及后续 4 MiB 区间前人为加 3.5 秒响应延迟。要求实际出现长帧间隔或时钟推进不足，并由诊断定位到等待上游响应。用例通过表示成功复现卡顿。 |
| 4K 能力 | 18 秒运动样片，HEVC Main10/AAC，3840×2160、24 fps、实测至少 35 Mb/s。按与 1080p 相同标准记录可连续出帧、卡顿或无首帧。本项记录 API22/x86 的能力结果，并检查报告存在。 |
| 真机验收 | 同版本和同签名 APK，使用目标设备与真实账号，记录稳定网络下普通 1080p、高码率 1080p、4K 原盘的首帧、缓冲、掉帧和持续播放。硬软解无法确认时填未知。手机、长虹 ARMv7 电视以及 HDR/多声道输出分别验收。 |

样片由 `scripts/prepare-tv-load-fixtures.sh` 生成并用 ffprobe 核验。Android 预览工作流执行主机传输测试、基础回归与高码率测试。APK 独立打包，必测项目通过后才上传。报告包含原始构建标识、样片元数据和数字结果。发布脚本核对 APK 与报告是否来自同一次运行。4K 探索结果包含卡顿和无首帧。

本地传输回归可在 `android-tv` 目录运行 `./gradlew testDebugUnitTest`。在 GitHub Actions 对指定分支运行 `Android TV API 22 preview`，可重跑完整验收。每轮保留 `android-tv-api22-evidence` 制品，其中 `.harness/tv-playback/load-report.json` 记录高码率测试，`load-1080-fixture.json` 和 `load-4k-fixture.json` 记录两份样片规格，`stream-diagnostics.png` 记录现场数据和遥控器焦点。

现场问题可直接使用「音轨／字幕 → 取流诊断」。等上游响应包含建立连接、等待 HTTP 响应头和跳转请求时间，读视频数据测量响应体读取，写给播放器测量本机套接字写入。五秒速度是按已转发字节计算的近似值。正常暂停、缓冲已经充足或请求取消时，低转发速度本身不能说明网络故障。观察正在卡住时哪一项的当前计时持续增长，再结合播放时钟和掉帧作判断。诊断仅保存在本次播放连接内，摘要不保存文件名、账号、地址、Cookie 或原始错误正文。

首轮正常 1080p 在 12.083 秒推进 11.999 秒，显示 324 帧。延迟组在 12.144 秒推进 2.920 秒，显示 81 帧，最长出帧空档 4.553 秒，上游最长等待 3.526 秒。运行因旧系统未能进入二级诊断入口停在 UI 用例，未验收 4K，也没有上传安装包。[首轮报告](https://github.com/StQuasimodo/Media-Library/actions/runs/44890329051)

第二轮的 4K 在 12.042 秒推进 11.763 秒，只显示 62 帧，最长出帧空档 2.808 秒。同一轮上游响应最长 21 毫秒，读取最长 24 毫秒。该次运行的诊断 UI 步骤仍失败，未上传安装包。[第二轮报告](https://github.com/StQuasimodo/Media-Library/actions/runs/44891270422)

## 0.3.0-alpha.17 验证记录

源码 `f0de77205f846ec2f30b019ff68f149128b1b079` 的 API22/x86 完整回归通过，包括 6 项传输测试、正常 1080p、1080p 卡顿复现、遥控器打开诊断与复制摘要、基础播放及 12 项同签名升级检查。4K 未达到连续出帧门槛。[构建和报告](https://github.com/StQuasimodo/Media-Library/actions/runs/44891927518)

| 条件 | 窗口／播放时钟净推进 | 实际显示帧数 | 最长出帧空档 | 最长上游响应等待 |

| 1080p H.264，24.4 Mb/s | 12.044 秒／12.002 秒 | 358 | 607 毫秒 | 23 毫秒 |

时钟净推进取窗口首尾读数并下限为零。缓冲时的结束时钟值可能回落，需结合出帧数、出帧间隔与等待判断。4K 在本轮取流响应较快且播放时钟推进正常，约 288 帧的窗口只显示 89 帧，应优先排查模拟器解码和渲染。已验证的取流故障和模拟器出帧问题都无法代替对真实夸克会话、目标电视及原盘文件的验收。

## 0.3.0-alpha.18 分段等待回归

前台夸克原画会话完成首段范围校验后，可同时提前请求最多四个后续分段。每段至多 4 MiB，响应体从套接字按序读取，沿用 64 KiB 转发缓冲。整个进程只给一个流分配这个并发窗口。短范围、字幕和 HLS 沿用串行路径。检测到范围或资源版本不一致时中止拼接。预请求被拒绝时取消同窗口的其余请求，并从当前偏移重新串行请求。

固定样片和每段 3.5 秒延迟沿用 alpha.17 的基线。新门槛要求实际遇到至少 3 秒响应等待，仍通过连续播放标准。另用每段 9 秒延迟验证严重缺数时的故障诊断。比较结束时进程 PSS 与最长出帧间隔时，以同一环境的同一延迟用例为准。

同一台 Linux 主机上的生产 `MediaTransfer` 传输对照使用 85,457,553 字节的 1080p 样片。服务端从第二段起对每段响应头延迟 3.5 秒，消费端将数据直接写入 SHA-256 计算器。串行路径耗时 70.50 秒，提前请求路径耗时 17.57 秒。两者均发出 21 次请求，输出均与源文件摘要 `77a0348cbd722b3e0d386c1020c93d37072291d89f3f251e2e580e4244fabf21` 匹配。

首轮 Android 5.1 测试中，延迟 3.5 秒的 1080p 样片最长出帧空档降至 604 毫秒。后续重连测试在主线程关闭未读的 HTTPS 响应体时触发 `NetworkOnMainThreadException`，该轮没有生成可分发的安装包。修复后会话取消只中止请求，响应体由中转线程释放。[首轮运行](https://github.com/StQuasimodo/Media-Library/actions/runs/45752524088)

最终 API22/x86 完整回归通过，构建源码为 `5fa483c`。同一 3.5 秒分段延迟下，首帧 4.658 秒，随后 12.109 秒显示 331 帧、丢失 37 帧，最长出帧空档 626 毫秒，结束时进程 PSS 156,221 KiB。alpha.17 同条件最长空档 7.429 秒，结束时 PSS 153,693 KiB。9 秒延迟仍复现 4.465 秒出帧空档。4K Main10 在 12.023 秒内显示 109 帧，结束时进程 PSS 614,574 KiB，未达连续播放门槛。正常 1080p 本轮显示 316 帧、丢失 51 帧，虽然通过现有门槛，仍需长时出帧测试。[完整回归](https://github.com/StQuasimodo/Media-Library/actions/runs/45775034935)
