# TV 云端 HLS：回看、换链与持续播放

TV 开发预览 `0.3.0-alpha.8` / versionCode16，承接 [alpha.7 试播 PoC](TV-QUARK-HLS-POC.md)。本阶段只修正取流生命周期并补齐稳定性验证，不更换播放器内核、登录方式或数据库。

## 修复

原先 `CloudHlsSession.resource` 每次解析某个访问过的分片时，都会把它最后使用的根地址当作失效地址。一旦 `MediaTransfer` 的8项地址 LRU 淘汰该分片，回看就会无故重新请求云端版本。有效地址也可能反复刷新，增加拖动等待与控制 API 限流风险。

现在区分首次解析/缓存未命中与已到期/401/403刷新。`MediaTransfer.Provider.refresh` 默认沿用原文件现有解析行为；云端实现将每份分片 Lease 与实际签发它的根 Lease 绑定，不依赖节点上可被覆盖的“最后一次根地址”。只有仍是当前根的失效请求才重新查询；并发旧请求共用已经取得的新根。绑定跟随有界 Lease 缓存和在途请求，不新增常驻历史映射。

普通回看重新从有效清单取出分片地址，不增加控制 API 调用。地址真正到期仍主动更新；401/403仍重取一次，并保留同源HTTPS、清单身份/时间轴校验、4MiB闭合Range和字节一致性保护。原文件 Provider 默认行为、收藏/媒体身份、凭据、挂载目录、原文件进度与备份格式不变。

## 新增实际链路检查

以下通过真实生产端点与独立HTTPS夹具执行，不在应用加入测试开关：

1. 先访问8个其他分片，让初始化段地址被 LRU 淘汰；回看初始化段应字节相同且不增加云端版本查询。
2. 两个不同分片同步返回403，使用服务端屏障保证真的发生并发过期；两个输出均需字节相同，云端根仅刷新一次。
3. 分片正文发送64KiB后断开并使原签名失效；有限重试应从准确偏移恢复，200001字节前后完全一致。
4. 子清单响应头已到、正文阻塞10秒时，在主线程关闭试播；本机读取须被取消，关闭不能等待网络超时或清单锁。
5. 真实LibVLC保持同一个解码器，对约60秒目标分片注入断流+过期，实际恢复并显示新帧；随后连续播放至少90秒，每5秒时钟与显示帧数均推进，总媒体时长推进至少85秒。
6. 记录云端流连续阶段的掉帧、进程CPU时间、起止PSS/每5秒最大采样PSS、应用files/cache体积变化和上游最大Range。采样最大PSS不是精确峰值；磁盘体积检查不能单独证明所有I/O行为，需结合生产代码无电影磁盘写入路径判断。
7. 继续全部已有定位、遥控器暂停、暂停重连、退出续播、原文件进度隔离、原文件90秒、备份与同签名升级检查。

Java主源码/instrumentation本地编译、17项取流策略和234项业务测试通过。完整Gradle/Lint、签名/API21/ARMv7+x86打包和API22/x86实际链路结果等待CI执行；测试定义不等同于已通过。

## 边界

继续使用合成180秒1080p H.264/AAC fMP4 HLS；不是真实夸克账号或真实电影。90秒检查属于短时稳定性样本，不等同数小时观影验收。当前环境没有绑定夸克凭据，真实账号、真实CDN覆盖率、长虹55D2S/ARMv7运行、4K/HDR及云端字幕音轨一致性仍未验收。云端试播进度独立保存，暂未纳入备份；没有新增电影本地缓存。未发布Release或更新feed。
